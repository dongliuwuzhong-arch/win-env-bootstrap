## 二、新发现问题（本轮更新引入，8 项）

### N1【P1】pyb/pys 硬编码路径检测的坏分支必然崩溃——检测能力回归（实测复现）
- **问题**：h-workspace.js:57 消息里引用已删除的 `curUser` 变量：`'当前用户是 ' + curUser`。路径不匹配分支触发时抛 ReferenceError，被外层 `catch { warn(wrap + ' 读不了') }`（:62）吞掉。
- **实测复现**：构造 `_tools/pyb.cmd` 含 `"C:\Users\OldUser\tools\pyb.exe"`、DSH_HOME/DSH_WORKSPACE 指沙箱 → `verify --only=H` 输出 **「⚠ pyb.cmd 读不了」**——既没报出真正的"写死了旧用户路径"（bad），还把代码缺陷伪装成文件读不了。
- **影响**：该检查存在的唯一目的（换机/换用户名后 pyb/pys 静默断链的预警）在**唯一需要它的场景**失效；误导用户查文件权限。
- **触发条件**：pyb.cmd/pys.cmd 里硬编码的用户路径 ≠ 当前用户（换机必现）。
- **修改建议**：`curUser` → `ctx.HOME`；并把该分支拆出独立 try 或先构建字符串再 push，避免消息拼接异常吞掉整个检测。
- **预期结果**：路径不匹配时输出「✗ pyb.cmd 写死了 C:\Users\OldUser，当前用户是 C:\Users\<me> —— 会静默断」。
- **验收标准**：① 新增契约测试：fake ctx 下 pyb.cmd 含异用户路径，断言输出含 `写死了` 且 level=bad；② 该测试在改回 `curUser` 引用时必须红（跑红验证）；③ `node --test` 全过。

### N2【P2】G2 relink 非原子：junction 创建失败后旧包停在 .bak 名下，等于删包
- **问题**：bootstrap.ps1:108-112 `Rename-Item $dst → $bak` 与 `New-Item -ItemType Junction $dst` 在同一 try；若 junction 创建失败（目标不可用/权限/杀软），catch 只报 "relink failed"，**$dst 已改名且未回滚**——profile 里该包消失，三个预设加载期 throw。
- **影响**：-Apply/-RepairG2 在异常路径上把"能跑但会失配"变成"直接不能跑"，比修复前更糟。
- **触发条件**：relink 时 junction 创建失败（低概率但后果重）。
- **修改建议**：catch 内回滚——`if (Test-Path $bak) { Rename-Item $bak → $dst 原名 }`；或先建 junction 到临时名再原子交换。
- **预期结果**：任何失败路径结束后 $dst 要么是原拷贝、要么是新 junction，绝不消失。
- **验收标准**：Pester 新增用例：Mock `New-Item` 抛错 → 断言 $dst 仍存在（原内容）且输出含 rollback 提示；变异验证（去掉回滚）测试转红。

### N3【P2】Install-Pkg pathDirs 回退的复测探针永远失败——确认逻辑是死代码
- **问题**：bootstrap.ps1:412-414 `Add-PathEntry $d` 只写注册表 User PATH，**不更新当前进程 `$env:Path`**；随后 `Get-CmdVersion` 用进程 PATH 解析命令，新目录不可见 → `if ($probe) { break }` 永不成立。多候选目录时会被连续全量加入 PATH；最终消息仍是 warn "restart the shell"，`[FIX]` 只来自 Add-PathEntry 自身。
- **影响**：泛化补 PATH 的价值打了折扣（首跑退出码虚高、无法确认修复、多候选时可能多加条目）；与"装完复测"的设计意图相悖。
- **触发条件**：任何 -Apply 后"装了不在 PATH"的工具（不止 7-Zip）。
- **修改建议**：Add-PathEntry 成功后同步 `$env:Path += ';' + $dir`（仅进程内，供复测），或在回退块内手动更新后复测；复测成功输出 `"$label installed via pathDirs ($probe)" 'fix'` 并 break。
- **预期结果**：补 PATH 后当次运行内即可确认解析成功，报 [FIX] 且 gap 闭合。
- **验收标准**：Pester：桩 pathDirs 下跑 Install-Pkg → 断言复测 probe 非空、输出含 'fix'、进程内 `$env:Path` 含新条目；仅加第一个命中的 pathDir。

### N4【P3】verify.mjs:144 `void started` 死变量
- **问题**：流式改造后 `started` 赋值未使用，留 `void started` 消音。
- **修改建议**：删掉；或实现为长段耗时展示（render 时打 `（耗时 Xs`），与 P1-1 的"长耗时段反馈"目标闭环。
- **验收标准**：`grep started scripts/verify.mjs` 无死变量；若实现耗时展示，M 段等待提示与完成行都带秒数。

### N5【P3】pyb/pys 比较用 startsWith 有前缀越界误判
- **问题**：h-workspace.js:56 `ctx.HOME.startsWith(hardUser)`——`C:\Users\Tom` 会把 `C:\Users\Tommy` 判为命中（ok 假绿）。
- **修改建议**：改为 `HOME === hardUser || HOME.startsWith(hardUser + '\\')`（大小写归一后）。
- **验收标准**：契约测试覆盖 `Tom` vs `Tommy` 边界，断言判 bad。

### N6【P3】tool_discover 注释承诺 "带 usage"，实际返回无 usage 字段
- **问题**：server.mjs:139 注释与实现不符（返回仍是 `{matched, tools}`）。
- **修改建议**：无过滤条件时返回增加 `usage: '用 capability 或 keyword 过滤，如 {"capability":"media:probe"}'`；或改注释。
- **验收标准**：mcp 测试断言无参调用返回体含 usage 或注释与实现一致。

### N7【P3】p-integrity-migration.js:68 persona srcs 清单仍硬编码四件套
- **问题**：h 段已改读 `manifest.personaFiles`，p 段做 AGENTS.md 时间比对时仍写死 `['SOUL.md','IDENTITY.md','USER.md','MEMORY.md']`——manifest 增删人格文件后两段分叉（P1-2.3 的同类残留）。
- **修改建议**：p 段同样读 `ctx.manifest.personaFiles`（fallback 保留）。
- **验收标准**：ps-tests-contract 的「g2/h 消费 manifest」锚点扩到 p 段；改 manifest.personaFiles 后两段行为一致。

### N8【P2】凭据检查被自身注释模板假绿——"文件在≠key在"并未真正检测
- **问题**：g2-plugin-prereq.js:197 起，判定是 `txt.includes(keyName)`；而 bootstrap 写出的注释模板本身就含 `OPENCODE_GO_API_KEY` 字样（bootstrap.ps1 模板行）。模板落盘后下一次 verify 立即报「凭据含必需 key」✅——恰恰是该检查声称要防的"文件在≠key在"。旧代码同语义（既有问题），但本轮刚把该段 manifest 化，检测语义未趁势修正。附带：readFileSync 整文件进内存与上方注释「凭据不整文件进内存」矛盾。
- **影响**：新机凭据没填 key 时 G2 段假绿，00 段也报「填 .credentials.yaml」ok（只查文件存在）——两道防线全空。
- **修改建议**：判定改为「存在非注释行（去 `#` 前缀空白后）匹配 `^\s*KEY_NAME\s*:\s*\S`」（值非空）；流式读回归或至少改注释；00 段 credentials 态可复用同一判定。
- **预期结果**：只有模板（全注释）时报 bad「key 未填值」；填了真实值才 ok。
- **验收标准**：契约测试三态：空文件 bad / 纯注释模板 bad / 含 `OPENCODE_GO_API_KEY: sk-xxx` ok；跑红验证。

## 五、架构建议：通用换机内核与 DSH 专属层分离（本轮新增要求）

> 现状：18 段里 00/G/G2/H(人格)/L/M/N(部分)/P(部分) 强绑定 DSH 生态（`~/.dsh`、DSH 宿主、profile 手工包、人格四件套）；A–F/I/J/K/O 才是通用 Windows 环境能力。非 DSH 用户跑一次 verify 会被 DSH 红条刷屏，「换机检测」这个通用能力被专属层绑架。建议拆成「通用内核 + 可选 DSH 包」。

### 5.1 模块边界（三层，依赖单向：dsh → core，core 永不引用 DSH 概念）

| 模块 | 内容 | 依赖 | 默认 |
|---|---|---|---|
| **core 通用内核** | A 核心运行时（Node/Python/Git/curl/winget/pnpm/rg/jq）、B 归档、C 媒体、D 浏览器、E 逆向、F Python 包（system 清单）、I 系统配置（PATH/执行策略/ConPTY build）、J 网络、O 系统环境（Defender/w32time/字体/LongPaths/磁盘）、K 代理启动器、PATH 补缺/去重/备份、挂起重启检测、tweaks 系统调优、`-ExportInventory`、MCP `tool_discover/tool_resolve` | 仅 Windows + winget/pip/npm | **启用** |
| **migration 迁移检测**（core 的一部分或并列） | P 段的端口/单实例/根证书 CA/工作区 ACL/实测可写、备份文件生命周期 | 无 DSH 依赖 | **启用** |
| **dsh-pack 专属层** | 00 人工前置（DSH 四件）、G DSH 本体、G2 插件加载前置（junction/手工包/本地插件/win-bash/uv/凭据）、H 的人格四件套与技能库、L 工作区脚本可跑性、M dsh-selfcheck、N 中 DSH 项（ChatTrace/TTS/soul 环境变量）、P 中 AGENTS.md/DSH_WE_DATA_DIR/自启 vbs、F 中 `dshBundled` 包、`-RepairG2`、MCP `env_status` 中对应段 | `~/.dsh`、DSH 宿主、工作区人格 | **可选（auto）** |

边界规则：
1. core 的检查/安装代码不得出现 `.dsh`、`DSH_ROOT`、persona、G2 等符号（现有 `ps-tests-contract` 锚点可直接扩展成模块边界守卫）；
2. dsh-pack 可以读 core 的 ctx（工具解析、run 封装），反向禁止；
3. manifest 是唯一清单源：`tools[]` 增加 `module: "core" | "dsh"` 标记，`categories[]` 同样加 `module` 字段。

### 5.2 可选启用方式（三种入口，同一判定源）

| 入口 | 语法 | 行为 |
|---|---|---|
| 自动探测（默认） | 不加任何参数 | `DSH_ROOT` 或 `~/.dsh` 存在 → 启用 dsh-pack；否则自动关闭并输出一行 info「未检测到 DSH 环境，跳过专属段（00/G/G2/H人格/L/M/N/P-DSH）」 |
| 显式开启/关闭 | `verify.mjs --profile=core\|dsh`；`bootstrap.ps1 -Profile Core\|Dsh`；环境变量 `DSH_MODULES=core,dsh` | 显式指定覆盖探测 |
| 组合过滤 | 现有 `--only=A,G2` 保留 | 段级粒度不受影响 |

退出码语义不变（0/1/2/64），但**计数只统计已启用模块**——非 DSH 用户的退出码不再被 G/G2 红条污染（今天 verify 在无 DSH 机器上必然 exit 1）。

### 5.3 通用内核的适用范围

- **目标用户**：任何换机/重装 Windows 的开发者与办公用户——不装 DSH、不用 persona，只要"新机器把常用工具配齐 + 自检 + 出报告"；
- **适用系统**：与现支持矩阵一致（Win11 x64 ✅ / Win10 1809+ ⚠️ 预计可用 / ARM64·离线 ❌）；不在本轮扩展；
- **能力边界**：只做「公开工具的安装/补缺/检测 + Windows 配置体检 + 清单导出/调优」，不碰任何应用本体（DSH 不装、其他应用本体同样不装——口径统一）；
- **裁剪验证**：`manifest.tools` 去掉 `consumer` 指向 DSH 的条目后，core 安装清单仍是自洽完整工具链（Node/Python/Git/7-Zip/ffmpeg/yt-dlp/ImageMagick/Chrome/rg/jq/exiftool/dotnet + pip 通用包）；
- **与 dsh-pack 的关系**：DSH 用户 = core + dsh-pack（现状体验不降级）；非 DSH 用户 = core（今天完全用不了的人群）。

### 5.4 迁移路径（最小改动，4 步）

1. manifest 加 `modules` 与 `categories[].module` / `tools[].module` 标记（纯数据，不动逻辑）；
2. verify/bootstrap 的段过滤按启用模块收窄（复用 `--only` 机制 + auto 探测），dsh 段未启用时打一行 info 而非红条；
3. 00 段改写为「通用前置（winget/网络/磁盘）」+「DSH 前置」两截，前者留 core；
4. 测试与文档：新增 `generic-profile` 契约（无 DSH 沙箱下 `--profile=core` 断言无 G/G2/00 段、exit 不受其影响）；README 增「两种用法」（通用换机助手 / DSH 二阶段）。

**预期结果**：非 DSH 用户一条命令得到可用的通用体检+装机体验；DSH 用户感知不变。
**验收标准**：① 无 DSH 沙箱 `verify --profile=core --json` 无 dsh 段且 exit 0/2；② 有 DSH 环境默认跑与今天输出等价（锚点测试比对段集合）；③ core 源码守卫测试（无 `.dsh` 符号）全绿；④ README 双语同步。

## 七、结论与最小收尾路线

**更新是否完整满足原要求？——方向满足，完成度约 70%，不能算"完整"。** 23 项中 9 项干净利落、8 项修了但留尾巴（其中 P1-2 的修复引入了必现的检测回归 N1）、6 项合理留账。测试从 117+21 增至 122+23 且新增锚点质量不错（manifest 单源守卫、DSH_HOME 守卫都是好设计），但**坏分支无覆盖**这一课说明「判据必须能跑红」的纪律在修复侧没有被同等执行。

**最小收尾路线（一个 PR 内可完成）**：
1. **R1**（curUser 回归，一行修复 + 坏分支测试）——必须最先做，它让一项已"修完"的能力实际上处于失效状态；
2. **R2 + R3 + R4**（relink 原子性、pathDirs 复测、凭据假绿）——三个都是"修复本身的新缺陷/旧语义残留"，各约半小时；
3. **R6** 五件小修打包；
4. **R5** 裸机实测按清单执行并归档——做完这一条，首轮 P0 关闭，"开箱即用"才从承诺变实证；
5. 第五节的模块化（core/dsh-pack）作为下一阶段独立 PR，不阻塞本轮收尾。

**一句话总结**：这轮更新把首轮清单当成了任务列表认真执行（值得肯定），但交付前少了一次"构造会失败的输入"的自检——补上 R1–R4 四个点、跑完裸机清单，它就配得上首轮报告里那句「把招牌立得住」了。
