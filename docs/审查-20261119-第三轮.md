## 一、严重问题（5 项 = 本轮新增 2 + 上轮遗留 3）

### 严重 #1（本轮新增）：CI 12 次运行全部失败 —— 回归门禁完全失效

- **问题**：GitHub Actions API 显示 `total_count: 12`，`conclusion` 全部为 `failure`，包括最新 `8287449`。失败点：`bootstrap -Check（只读，断言退出码）` 步骤（其后 smoke.ps1 被 skip）。
  **根因（已本地复现）**：GitHub Actions 的 pwsh/powershell shell 包装器会在每个 run 步骤末尾追加 `if ((Test-Path -LiteralPath variable:\LASTEXITCODE)) { exit $LASTEXITCODE }`。CI 步骤脚本体里 `bootstrap.ps1 -Check` 返回 **合法退出码 1**（CI 机没装 DSH，有硬缺口），断言 `$code -notin 0,1,2` 通过、脚本体正常结束，但包装器随后 `exit $LASTEXITCODE`（=1）→ **步骤判失败**。即：只要 bootstrap 返回非 0（在无 DSH 的 CI 机上恒成立），这条步骤永远红。
  本地复现输出：`step sees exit = 1` → `步骤最终退出码 = 1`（断言明明通过）。
- **影响范围**：整个 CI。契约测试、语法检查虽过但被这条拖死；`smoke.ps1` 步骤永远 skip。**实际上项目现在没有任何有效的自动化回归**，MAINTAINING.md 的"改完三验"里 CI 那道防线是假的。
- **触发条件**：任何 push/PR（12 次全中）。
- **修复方向**：CI 步骤脚本体末尾显式 `exit 0`（在断言通过后），或 `$global:LASTEXITCODE = 0`，或把断言改成 `exit 0`/`exit 1` 显式退出而不靠包装器。同样检查 `smoke.ps1` 步骤（当前它期望 0，暂不漏，但建议统一封尾）。
  ```powershell
  # ci.yml bootstrap -Check 步骤末尾改为：
  if ($code -notin 0,1,2) { Write-Host "::error::..."; exit 1 }
  exit 0   # ← 必须显式封尾，否则包装器泄漏 bootstrap 的 1
  ```
- **验证步骤**：
  ```bash
  # 1) 修前确认（看 GitHub Actions）：任一 run 的 "bootstrap -Check" 步骤红，其命令体无 error 输出
  # 2) 本地模拟包装器泄漏（已验证）：
  #    写一个 ps1：调 bootstrap -Check；断言 0/1/2；末尾加 GH 包装器行 exit $LASTEXITCODE
  #    → 期望复现 exit=1；去掉泄漏后 exit=0
  # 3) 修后推一次：Actions 全绿（bootstrap -Check 步骤 exit 0，smoke 步骤执行且过）
  ```

### 严重 #2（本轮新增）：MAINTAINING.md 交接文档失真 —— 已知缺陷表漏记 + CI 状态误述

- **问题**：
  1. `MAINTAINING.md` 的「已知缺陷 / 没做的」表**完全没提**上轮报的 3 个严重缺陷（puppeteer 死代码、frida 不装、workspace 解析不一致）。
  2. 表里写「CI 实跑：workflow 只在本地推演过，**没在 GitHub Actions 上跑过**」——**与事实矛盾**：Actions 有 12 次运行记录，全部失败（见严重 #1）。文档说"没跑过"，实际是"跑过且全红"。
  3. 「怎么确认你没改坏」给的三验包含 CI 语义，但 CI 实际不工作。
- **影响范围**：该文档是给"接手维护者"的唯一交接材料。漏记 3 个严重缺陷会让维护者以为代码是干净的；CI 误述会让人以为"还没接 CI"而不会去查为什么红。
- **触发条件**：任何新维护者按 MAINTAINING.md 判断项目健康度时。
- **修复方向**：把 5 个严重项补进已知缺陷表（含触发条件与验证命令）；CI 状态改为「已接入但当前全红，根因见 xxx」；建议在 MAINTAINING.md 顶部加"本文档随缺陷清单同步更新"的维护约定。
- **验证步骤**：`grep -c "puppeteer\|frida\|workspace" MAINTAINING.md` 修后应 >0；文中对 CI 的描述应与 `curl .../actions/runs` 的结论一致。

### 严重 #3（遗留）：`$wsPath` 在赋值前使用 —— puppeteer 自动安装块是死代码

- **问题**：`bootstrap.ps1:466` 用 `$wsPath`，但赋值在 `:498–504`。`Join-Path $null` 抛参数绑定异常，整个块静默跳过（`$ErrorActionPreference='Continue'`）。上轮已复现，本轮 diff 确认零改动。另 puppeteer 有两块重复逻辑（465–481 死块 + 505–507 只报块）。
- **影响**：`-Apply` 装不了 puppeteer，fetch-render.mjs 持续不可用；stderr 刷绑定错误。
- **触发**：任何机器（恒不执行）。
- **修复**：把 workspace 解析块上移到 C 段前；合并重复块为「检测→安装→复测」；加 `if ($wsPath)` 守卫。
- **验证**：`Select-String -Path scripts\bootstrap.ps1 -Pattern 'wsPath' | Select LineNumber` → 赋值行号应 < 全部使用行号；在有 `_tools\browser\package.json` 无 `node_modules` 的目录跑 `-Apply`，应出现 `installing puppeteer ...` 且产物落盘。

### 严重 #4（遗留）：frida / 微信 4 包 / DSH python 缺包仍无安装动作

- **问题**：`bootstrap.ps1:511–513` frida 仍只 warn（manifest 的 `pip: frida-tools` 无人消费）；cryptodome/zstandard/pysilk 与 DSH python 缺包无任何安装动作。
- **影响**：换新机后 wechat-history 取证与 DSH python 工具链仍需人工逐个 pip install。
- **触发**：全新机器 `-Apply` 后 E/F 段仍报缺。
- **修复**：补 `pip install frida frida-tools`、按解释器分别补装微信 4 包与 DSH python 核心包（f-python-packages.js 已区分两套解释器，照此对齐）。
- **验证**：`bootstrap.ps1 -Apply` 后 `node scripts/verify.mjs --only=E,F` 应转绿。

### 严重 #5（遗留）：工作区解析双脚本不一致 —— 同机两结论

- **问题**：`bootstrap.ps1:498–504` 兜底 `C:\DSH空间`；`paths.js:55–58` 兜底空串，且优先级顺序也不同（verify 把 manifest.default 排在 env 前，bootstrap 相反）。未设 `DSH_WORKSPACE` 的机器：bootstrap 报 `[OK] workspace: C:\DSH空间`，verify 报 `✗ 工作区不存在: `（空路径）。
- **影响**：MCP `env_status` 与人工跑 bootstrap 结论矛盾，破坏"实时反馈"可信度；新机最典型场景必中。
- **触发**：`manifest.workspace.default` 为空 + 未设 `DSH_WORKSPACE`。
- **修复**：统一解析顺序（参数 > env > manifest > 兜底）与兜底值；空路径时输出「工作区未配置（设 DSH_WORKSPACE 或改 manifest）」而非「不存在: 」。
- **验证**：
  ```bash
  node scripts/verify.mjs --only=00,H     # 未设 env 时
  # 与 bootstrap.ps1 -Check 对比工作区结论，应一致
  DSH_WORKSPACE="C:/DSH空间" node scripts/verify.mjs --only=00,H   # 设了都应绿
  ```
